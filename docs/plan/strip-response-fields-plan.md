# feat-046: `ResponseSchema` як allow-list полів відповіді

> Статус: план (не реалізовано). Дата: 2026-10-30. Залежить від feat-044.

## 1. Задача

Зараз жодна перевірка не зупиняє витік поля, якого немає в схемі:

- runtime-перевірка (feat-044) викликає `schema(payload)` і **відкидає** результат
  (`validate-response.ts:105`), а схеми не забороняють невідомі ключі;
- перевірка типів (feat-050) структурна й зайві поля дозволяє.

Якщо transformer пропустить, наприклад, `passwordHash`, відповідь пройде обидві перевірки.

Мета: для маршруту з `ResponseSchema` клієнт отримує **лише поля, описані в схемі**, на будь-якій
глибині. Відповідь, що не відповідає схемі, у будь-якому режимі дає 500 (fail-closed: інакше
неочищений payload з секретом пішов би клієнту). Зайві ключі в production вирізаються з
попередженням у лог, поза production дають 500. `RESPONSE_VALIDATION` перейменовується на `RESPONSE_VALIDATION_CONTRACT` і задає реакцію
на порушення контракту; режиму `off` більше немає (§4.2). Без `ResponseSchema` поведінка не
змінюється.

## 2. Що показав прототип

ArkType 2.2.8 (версія з `package.json`), схема — union з помилкою, як у `shared/responses`:

| Перевірка                               | Результат                                                                                                                                                           |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `.onUndeclaredKey('delete')`            | Вирізає лише верхній рівень: `{ n: { a, z } }` → `z` лишається. Для allow-list не годиться                                                                          |
| `.onDeepUndeclaredKey('delete')`        | Вирізає на всіх рівнях, у масивах і в обох гілках union                                                                                                             |
| Вхідний об'єкт                          | Не мутується: результат — новий об'єкт (`out !== input`)                                                                                                            |
| `Date`                                  | Лишається `Date` (морфів немає), серіалізується як раніше                                                                                                           |
| Поле `'unknown'` (`'data?': 'unknown'`) | Вміст **не фільтрується**: `data: { leak: 1 }` проходить                                                                                                            |
| Типи (`tsc`)                            | `inferIn` після `onDeepUndeclaredKey` той самий; метод є і на `BaseType`                                                                                            |
| Вартість                                | Див. таблицю нижче                                                                                                                                                  |
| `.onDeepUndeclaredKey('reject')`        | Зайвий ключ — помилка `code: 'predicate'`, `expected: 'removed'` зі шляхом (`items[0].passwordHash`); невідповідність типу — інший код (`domain`). Об'єкт не копіює |

Вартість (2026-10-30, локально; елемент із 8 полями, зокрема `Date` і масив, схема — union з
помилкою; медіана 7 серій після прогріву; скрипт — у `progress.md` T0.5):

| Елементів | `JSON.stringify` | Перевірка feat-044 | `reject`, без зайвих ключів | `reject` / JSON | Із зайвими ключами: `reject` → `strip` → шляхи |
| --------- | ---------------- | ------------------ | --------------------------- | --------------- | ---------------------------------------------- |
| 10        | 0.018 мс         | 0.014 мс           | 0.017 мс                    | 95 %            | 0.18 мс (10×)                                  |
| 100       | 0.174 мс         | 0.136 мс           | 0.164 мс                    | 95 %            | 1.72 мс (10×)                                  |
| 1000      | 1.82 мс          | 1.39 мс            | 1.69 мс                     | 93 %            | 17.9 мс (10×)                                  |

`reject` дорожчий за нинішню перевірку на ~20 %, але в production зараз `off`, тож уся ця вартість
там нова: приблизно ще одна серіалізація на відповідь. Шлях із зайвими ключами коштує ~10× через
збирання помилки на кожен зайвий ключ (у прикладі — по одному на елемент).

Морфів (`.pipe`, `.parse`, `.to`) у `packages/shared/src/responses` немає, тож результат схеми
відрізняється від входу лише видаленими ключами.

Полів `unknown` / `unknown[]` у схемах відповідей — близько 30: `details` у помилках (навмисно,
точний тип задано в TypeScript), `data` / `subscription` / `statistics` у push-subscription,
support, prompt, і службові маршрути `main-controller` (`/test-*`).

## 3. Аналіз впливу

### 3.1 Безпека — позитивний

- `ResponseSchema` стає allow-list: поле, якого немає в схемі, клієнт не отримає, навіть якщо
  transformer помилився. Це закриває клас витоків, який feat-044 і feat-050 не бачать за дизайном.
- Попередження в лог (шляхи вирізаних ключів, без значень) показує, де transformer повертає
  зайве.

### 3.2 Мінуси та ризики

- **Вартість.** Схема тепер виконується на кожну відповідь і в production. Звичайна відповідь
  коштує одну перевірку `reject` без копіювання; копія (вирізання) — лише для відповіді із зайвими
  ключами (§4.3). Аварійного вимикача немає, тож бенчмарк T7 із числовими критеріями —
  обов'язковий до merge.
- **500 у production.** Fail-closed для невідповідності схемі означає, що ще не знайдені
  розбіжності в production стануть 500. Тому аудит T2 і період на staging — умова ввімкнення
  (§4.6).
- **Поля `unknown`** — діри в allow-list: вкладені дані в них не фільтруються. Межа гарантії —
  §4.5.
- **Зміна відповідей.** Будь-яке поле, яке зараз іде клієнту без опису в схемі, зникне. Фронтенд
  може на нього розраховувати. Потрібен аудит до ввімкнення (T2).
- **Breaking change конфігурації.** `RESPONSE_VALIDATION` перейменовується, `off` і sample rate
  зникають. Стара назва приймається один реліз з попередженням (§4.4).
- **Різна поведінка dev/prod для зайвих полів** (500 проти вирізання) — навмисна: dev має
  помітити помилку transformer'а, production — не впасти й не злити поле.

### 3.3 Чого не дає

- Не фільтрує вміст полів `unknown`: дозволені винятки перелічені в §4.5, для них гарантії немає.
- Не змінює формат `Date` → ISO-рядок — це feat-047.
- Не стосується 3xx / 204 / 205 і порожніх відповідей: тіла там немає, як і в feat-044.
- Не стосується асинхронних WS-повідомлень і broadcast — це feat-049.

## 4. Дизайн

### 4.1 Де вирізати: централізовано в бекенді

`createResponseCheck` будує з `ResponseSchema` маршруту другу схему
`schema.onDeepUndeclaredKey('delete')` **один раз** при реєстрації маршруту (`router.ts:46`).
Схеми в `shared/responses` не змінюються.

Чому не `'+': 'delete'` у кожній схемі в `shared`:

- 60+ схем, легко пропустити нову; централізоване правило діє на всі маршрути автоматично;
- фронтенд імпортує ті самі схеми з `shared/responses` (`api.ts`, `useOAuthProviders.ts`, admin
  views) — зміна їхньої поведінки зачепила б клієнт;
- `/doc/routes` і playground далі показують схему як є.

### 4.2 Режими: `RESPONSE_VALIDATION_CONTRACT`

`RESPONSE_VALIDATION` перейменовується на `RESPONSE_VALIDATION_CONTRACT`. Вона задає не «перевіряти
чи ні», а **як реагувати на порушення контракту відповіді**. Таких порушень два:

| Подія                 | Приклад                          | Можлива реакція                                            |
| --------------------- | -------------------------------- | ---------------------------------------------------------- |
| Невідповідність схемі | `status: 'fail'`, `total` рядком | вирізати неможливо (результату схеми немає) → 500 або як є |
| Зайві поля            | `passwordHash` у відповіді       | вирізати; додатково 500 або `warn`                         |

Режими (два, `off` немає). Невідповідність схемі — 500 в обох: вирізати таку відповідь
неможливо, а відправити як є означало б віддати клієнту й зайві поля, якщо вони там є (секрет
разом із неправильним `total`). Режими відрізняються лише реакцією на зайві поля:

| `RESPONSE_VALIDATION_CONTRACT` | Невідповідність схемі | Зайві поля        | За замовчуванням                 |
| ------------------------------ | --------------------- | ----------------- | -------------------------------- |
| `strict`                       | 500                   | **500**           | поза production (dev, CI, тести) |
| `log`                          | **500**               | вирізати + `warn` | production                       |

- **Вирізання є завжди**, окремого перемикача немає. Причина: ArkType вирізає ключі тим самим
  обходом, що й перевіряє (`onDeepUndeclaredKey` — режим валідації, а не окремий крок), тож
  режим «без перевірки, але з вирізанням» нічого не економить. Схема виконується на кожну
  відповідь у будь-якому режимі.
- **У `strict` зайве поле — 500, а не тихе вирізання.** Інакше в dev вирізання ховало б помилку
  transformer'а, і її ніхто б не виправив. Вирізання — страховка для production.
- **Sampling прибирається** (`RESPONSE_VALIDATION_SAMPLE_RATE`): схема однаково виконується на
  кожну відповідь, а allow-list, що діє на частині запитів, не захищає.
- Невідоме значення зупиняє старт (`validateRuntimeConfig()`).
- **Аварійного вимикача за продуктивністю немає.** Тому бенчмарк T7 — обов'язковий крок до
  merge, а не замір після. Якщо вартість неприйнятна — рішення в коді (§4.7), не в конфігу.

### 4.3 Реалізація режимів

`createResponseCheck` будує дві схеми на маршрут **один раз** при реєстрації (`router.ts:46`):
`reject = schema.onDeepUndeclaredKey('reject')` і (лише для `log`)
`strip = schema.onDeepUndeclaredKey('delete')`. Перевірка відповіді:

1. `reject(payload)`. Валідна → відправляється **вихідна** відповідь: зайвих ключів немає, копія
   не потрібна. Це шлях майже всіх відповідей, його вартість — одна перевірка.
2. Помилки є, і серед них є не лише зайві ключі → **500** (обидва режими), `error` у лог.
3. Помилки є, і всі вони — зайві ключі (`code: 'predicate'`, `expected: 'removed'`):
    - `strict` → 500, `error` у лог зі шляхами;
    - `log` → `strip(payload)`. Якщо `strip` повернув помилки (не мало б статися після кроку 3,
      але поведінка ArkType може змінитися) → **500**, вихідний payload не відправляється.
      Інакше відправляється очищений результат, `warn` у лог зі шляхами.

Обидва виклики схеми fail-closed: вихідний payload відправляється лише після успішного `reject`.

**Доповнення після рев'ю коду.** ArkType не бачить два випадки, тож після `reject` іде один
обхід відповіді (`inspectPayload`):

- власні ключі з іменами властивостей `Object.prototype` (`constructor`, `__proto__`,
  `hasOwnProperty`, …) — ArkType читає їх через прототип і пропускає в обох режимах; обробляються
  як зайві ключі (500 у `strict`, вирізання в `log`);
- значення, яке `JSON.stringify` серіалізує інакше, ніж бачила схема: усе, крім простого
  об'єкта, простого масиву й `Date` без власного `toJSON` (перелічуваного чи ні); підкласи `Date`
  і масиву теж. Перевіряється до винятків для `Date` і масивів; 500 в обох режимах.

Ознаку «зайвий ключ» (`predicate` + `removed`) ArkType не документує як стабільний контракт;
її фіксує окремий тест (T1), щоб оновлення ArkType, яке її змінить, впало в CI, а не в production.

`ResponseCheck` повертає не `boolean`, а результат:

```ts
type ResponseCheckResult =
    | { ok: true; payload: unknown } // що відправити: вихідна відповідь або очищена
    | { ok: false } // викликач відправляє 500
```

- `server.ts` (`checkHandlerResponse`) і `ws-api-dispatcher.ts` відправляють `payload` з
  результату замість відповіді контролера.
- Очищений результат відрізняється від входу лише видаленими ключами (морфів немає — §2).
- **Відправляється вихідний об'єкт, а не результат схеми** (крок 1). Це коректно, лише поки в
  схемах відповідей немає морфів — див. feat-047 у §4.6.

**Контракт логування** (фіксований, не залежить від T7): шляхи беруться з помилок `reject`, тож
порівняння ключів не потрібне й нічого не коштує на звичайному шляху. Кожен запис — лише шляхи,
коди й очікуваний тип, без значень (PII); rate-limit по маршруту, як у feat-044; Sentry з тегом
`response_validation`. Зайві ключі мають власний код у записі (`undeclared_key`), щоб їх можна
було відфільтрувати від невідповідностей. Шляхів у записі — не більше 20 (решта — лічильником
`truncated`): у списку із зайвим полем в кожному елементі їх тисячі.

### 4.4 Сумісність зі старою назвою

`RESPONSE_VALIDATION` уже описана в `.env.example`, `configuration.md` і в плані feat-045.
Один реліз стара назва приймається з попередженням у лог при старті:

- `RESPONSE_VALIDATION=strict|log` → те саме значення `RESPONSE_VALIDATION_CONTRACT`;
- `RESPONSE_VALIDATION=off` → `log` + попередження, що `off` більше немає;
- задано обидві змінні → перемагає нова, попередження;
- `RESPONSE_VALIDATION_SAMPLE_RATE` ігнорується з попередженням.

Після релізу стара назва прибирається окремим PR (запис у `feature_list.json`).

### 4.5 Поля `unknown`

Аудит усіх `unknown` у `shared/responses` (T2) з рішенням для кожного:

- **деталізувати** схему, якщо поле несе дані з БД (`subscription`, `statistics`, `data` у
  push-subscription, support, prompt);
- **лишити** `unknown` з коментарем, якщо вміст контрольований і без PII (`details` помилок —
  точний тип у TypeScript, `CanonicalErrorResponse`);
- службові `/test-*` маршрути `main-controller` — лишити, вони не в production-контракті
  (перевірити, що вони справді вимкнені в production).

**Межа гарантії.** Allow-list діє лише там, де схема описує структуру. Вміст поля `unknown`
(`'details?': 'unknown'`, `'data?': 'unknown'`) проходить без фільтрації на будь-якій глибині.
TypeScript-тип (як `ErrorDetails` у `CanonicalErrorResponse`) цього не змінює: він не перевіряє
значення під час виконання.

Тому критерій завершення фічі — не «кожне `unknown` має рішення», а:

- кожне `unknown`, що несе дані з БД або від користувача, **деталізоване** в межах фічі
  (push-subscription, support, prompt) — відкладати не можна;
- лишаються `unknown` лише явні винятки, перелічені в `documentation/backend/response-validation.md`
  як поля **без гарантії allow-list**, кожен з причиною: `details` помилок (будується лише з
  конструкторів `AppError`), службові `/test-*` маршрути (якщо підтверджено, що вони вимкнені в
  production);
- тест-охорона: список дозволених `unknown`-шляхів зафіксований, нове `unknown` у схемі відповіді
  валить тест, доки його не додано до винятків свідомо.

### 4.6 Зв'язок з іншими фічами

- **feat-050:** типи не змінюються (`inferIn` той самий, §2). Перевірка типів і далі дозволяє
  зайві поля; у `strict` їх ловить runtime як 500, у `log` — вирізає. Документація має розвести,
  хто що гарантує.
- **feat-047:** швидкий шлях (§4.3, крок 1) відправляє **вихідний** об'єкт і відкидає результат
  схеми; очищений результат відправляється лише при зайвих ключах. Якщо feat-047 додасть морфи
  (`Date` → ISO-рядок), формат відповіді залежатиме від того, чи були зайві ключі. Тому feat-047
  має: (а) переглянути швидкий шлях — відправляти результат `reject` (він уже з морфами) замість
  вихідного об'єкта; (б) замінити тест на ідентичність payload (T1) тестом на формат; (в) заново
  заміряти вартість. Тест-охорона морфів (T1) зупинить появу морфу без цього перегляду. Запис —
  у плані feat-047 (T8).
- **feat-045:** розкатка змінює зміст. `off` немає, а `log` тепер fail-closed для невідповідностей.
  Отже, ввімкнення в production — це вже 500 на розбіжностях. Умова: аудит T2 і щонайменше тиждень
  на staging у `log` без записів про невідповідність (зайві ключі допустимі — вони вирізаються).
  **Цю умову перевіряє власник feat-046** в межах цієї фічі: нова поведінка активна за
  замовчуванням, тож production-реліз з нею — частина feat-046, а не feat-045. feat-046 переходить
  у `done` лише з evidence staging-тижня (T10).
  Розкатка `log` → `strict` у production лишається задачею feat-045 (різниця тепер лише в
  реакції на зайві ключі); план і опис feat-045 оновити. Відкат у разі проблем — попередня версія
  бекенда, перемикача немає.

### 4.7 Критерії вартості і запасний варіант

Бенчмарк T7 приймається, якщо (медіана, той самий стенд і скрипт, що в §2; T0.5 підтвердив, що
пороги досяжні на прототипі):

- **звичайна відповідь** (без зайвих ключів): `reject` — не більше **1.2×** `JSON.stringify` тієї
  ж відповіді, не більше **+50 %** до перевірки feat-044 (було +30 %, змінено рішенням нижче), і в абсолютних числах не більше
  **0.25 мс** для 100 елементів і **2.5 мс** для 1000 (прототип: 0.95×, +20 %, 0.16 / 1.7 мс);
- **пам'ять:** на звичайному шляху копії відповіді немає (вихідний об'єкт — тест на ідентичність);
- **відповідь із зайвими ключами**, весь шлях `reject` → `strip` → логування: не більше **15×**
  `JSON.stringify` (прототип: 10×). Прийнятно, бо це шлях помилки transformer'а, а не норми;
  частку таких відповідей видно з логів `undeclared_key`, і кожна з них — баг для виправлення.

**Фактичний результат (після обходу `inspectPayload` з перевіркою serialization hooks):**
1.07–1.10× `JSON.stringify`, 0.20 / 1.98 мс для 100 / 1000 елементів, шлях із зайвими ключами
~10× — у межах. Поріг **+30 % до перевірки feat-044 не пройдено: +38–49 %** (обхід додає
~0.05 мс на 100 елементів). **Рішення (2026-10-30, власник):** межа до перевірки feat-044 —
**+50 %**: обхід — частина allow-list; решта порогів проходить.

Лишається поза перевіркою: перелічуваний getter, що повертає інше значення при другому читанні
(ArkType читає один раз, `JSON.stringify` — ще раз). Маршрутів із такими об'єктами немає;
перевірка дескрипторів кожної властивості коштувала б значно більше.

Межі — пропозиція плану, погоджуються в PR плану. Якщо T7 їх не проходить, фіча не мерджиться,
доки не знайдено рішення.

Запасний варіант — власний picker за структурою схеми (`schema.json`) без перевірки типів. Він
змінює семантику (немає перевірки типів, гілку union треба визначати самостійно, наприклад за
`status`) і потребує окремого плану й рев'ю — у цю фічу не входить.
