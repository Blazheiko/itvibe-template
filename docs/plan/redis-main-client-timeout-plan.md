# План: основний Redis-клієнт — швидка відмова замість зависання (пункт 70)

Джерело: пункт 70 у [code-issues-found-during-docs.md](./code-issues-found-during-docs.md), знайдено під час ручної перевірки feat-013.

Редакція 5. Зміни від редакції 4 за рев'ю: сигнал «команда відкладена паузою» — прапорець блокування й ім'я команди клієнта в `CLIENT LIST`, перевіряється spike на образі Redis з CI (а не `qbuf > 0`); дедлайн `logoutAll` враховує залишок бюджету під час кожного `await`.

Редакція 4. Зміни від редакції 3 за рев'ю: контрольний прогін тесту повторів має повну конфігурацію з чергою й очікуванням reconnect, а відправлення команди до `CLIENT KILL` підтверджується через `CLIENT LIST` (`qbuf`); тест застарілого знімка перевіряє саме запис (`saveSession`), а читання й запис в `updateSessionData` — окремим unit-тестом; визначено контракт межі `logoutAll` (дедлайн, `503`, без часткового успіху); відновлення CSRF — три команди.

Редакція 3. Зміни від редакції 2 за рев'ю: heartbeat (`ping`/`pong`) не залежить від Redis; інтеграційні тести розрізняють первинне пізнє виконання і повторне надсилання (через `CLIENT KILL` до виконання); здоров'я відновлюється і за першою успішною командою, і за фоновим `PING`, без потреби в reconnect; уточнено бюджет HTTP і рішення щодо логів у stdout.

Редакція 2. Зміни від редакції 1 за рев'ю: відмова від offline queue і повторного надсилання (таймаут не скасовує команду в черзі, а повтор `SETEX` може повернути застарілий знімок); Sentry — одна подія на інцидент через стан здоров'я клієнта і пропуск за типом помилки в транспорті, а не `warn` з `sentryCapture`; бюджет часу на весь запит, а не лише на команду; точний контракт WS-відповіді з початковим `event`.

## Проблема (відтворено вручну, feat-013, етап 9)

Коли Redis недоступний, будь-який запит, що читає сесію, висить ~45 с і завершується `500 internal_error` з текстом `MaxRetriesPerRequestError: Reached the max retries per request limit (which is 20)`. Upgrade з токеном правильного формату висить так само.

## Ризики, які план має закрити

1. **Короткий таймаут без розрізнення помилок** закриє всі WS-з'єднання при будь-якому короткому збої (reconnect storm) і дасть потік `500` у Sentry.
2. **Таймаут не скасовує команду.** В ioredis 6 таймер лише відхиляє Promise; команда в offline queue надсилається після reconnect. Клієнт уже отримав `503`, а запис сесії чи видалення відбудеться пізніше.
3. **Повтор після reconnect небезпечний для `SETEX`.** Це повний знімок сесії: повтор старого знімка після конкурентного оновлення чи видалення може повернути застарілі дані або відновити видалену сесію.
4. **Таймаут команди ≠ час запиту.** WS-повідомлення робить refresh і читання сесії послідовно, upgrade — читання токена і сесії; HTTP — читання і, для нової анонімної сесії, запис.
5. **Sentry:** `logger.error` є в багатьох місцях, а refresh викликається на кожне повідомлення.

## Рішення

### 1. Клієнт без черги і без повторів

Той самий контракт, що вже доведений для клієнта лімітів у feat-013, але з довшим таймаутом:

| Опція                           | Нове значення                                                     | Чому                                                                                                                                    |
| ------------------------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `enableOfflineQueue`            | `false`                                                           | поки з'єднання не `ready`, команда одразу отримує помилку, а не стає в чергу, тож не виконається пізніше без відома викликача (ризик 2) |
| `autoResendUnfulfilledCommands` | `false`                                                           | незавершена на момент розриву команда не надсилається знову: старий знімок `SETEX` не перезапише новіший (ризик 3)                      |
| `maxRetriesPerRequest`          | `0`                                                               | команда, що була в польоті під час розриву, одразу відхиляється                                                                         |
| `commandTimeout`                | `REDIS_COMMAND_TIMEOUT_MS`, default `500` (уточнити вимірюванням) | межа для повільного, але підключеного Redis                                                                                             |
| `retryStrategy`                 | `min(times · 100, 2000)` мс                                       | reconnect у фоні; на запити не впливає                                                                                                  |
| обробник `error`                | через модуль здоров'я (розділ 3)                                  | без `Unhandled error event` у консолі                                                                                                   |

**Що лишається:** команда, яку вже записано в сокет, сервер може виконати навіть після того, як клієнт отримав таймаут. Це неминуче для будь-якого мережевого виклику. Наслідки обмежені:

- в одному процесі одне з'єднання, а Redis виконує команди одного з'єднання по черзі, тож пізніша команда цього процесу не обжене ранішу (порядок записів у межах процесу зберігається);
- запізнілий `SETEX` при login створить сесію, про яку клієнт не дізнався (cookie не встановлено) — вона зникне за TTL;
- запізнілий `DEL` при logout видалить сесію пізніше — клієнт отримав `503` і повторить вихід;
- конкурентні записи з різних процесів у ту саму сесію існують і зараз; план їх не погіршує.

Ціна відмови від черги: короткий reconnect (частки секунди) теж дає `503` замість короткої затримки. Це прийнятно, бо HTTP отримує `Retry-After: 1`, а WS-з'єднання не закриваються (розділ 4).

### 2. Класифікація: `RedisUnavailableError` і перевірка стану до команди

- Нова помилка `RedisUnavailableError` (`vendor/utils/network/errors/`), `statusCode 503`, `code service_unavailable`.
- `isRedisUnavailable(err)` розпізнає помилки ioredis, що означають недоступність: `Command timed out`, `Connection is closed`, `Stream isn't writeable…`, `MaxRetriesPerRequestError`, `ECONNREFUSED`/`ECONNRESET`. Помилки Lua, `WRONGTYPE`, `SyntaxError` — **ні** (це баги).
- **Сервісний шар:** login, logout, `logoutAll` і генерація WS-токена проходять через `tryInternal`, який перетворює будь-який виняток на `Internal` → `500`. Тому додається тег `AppError` `ServiceUnavailable` (`503`), і `tryInternal` повертає його, коли причина — `RedisUnavailableError`; `mapControllerError` додає `Retry-After: 1` без технічного тексту. Інші причини — як зараз.
- Обгортка `withRedis(op)` у шарі сесій: якщо `redis.status !== "ready"` — одразу `RedisUnavailableError` без відправлення команди; інакше виконує `op`, а помилку недоступності загортає в `RedisUnavailableError`. Решту помилок пробрасує як є.

### 3. Здоров'я клієнта і Sentry: одна подія на інцидент

Модуль `database/redis-health.ts` слухає події основного клієнта і тримає стан `healthy | unavailable`:

- перехід `healthy → unavailable` (перша подія `error`/`close` або перша `RedisUnavailableError` з `withRedis`) → **один** `logger.error({ sentryCapture: true }, "Redis unavailable")` — рівень `error`, тож проходить у Sentry;
- повторні помилки в стані `unavailable` у Sentry не йдуть; сам модуль здоров'я пише `warn` не частіше разу на хвилину (це обмеження стосується лише його, а не інших логів збою — див. нижче);
- **відновлення** — за першим із сигналів, бо після таймауту без розриву нового `ready` не буде:
  - будь-яка успішна команда через `withRedis` у стані `unavailable`;
  - фоновий `PING` раз на 2 с, поки стан `unavailable` (таймер зупиняється в `healthy`), — щоб виявити відновлення й без трафіку;
  - подія `ready` після reconnect;

  → `logger.info("Redis recovered", { downMs })`, стан `healthy`; наступний збій знову дає одну подію;

- одна подія на інцидент **на процес**: N інстансів дадуть N подій — у документації це зазначено; агрегацію між процесами робить сам Sentry (групування за повідомленням).

Щоб інші `logger.error` не дублювали подію:

- `sentryStream` пропускає записи, де `err.type === "RedisUnavailableError"` (поле, яке серіалізатор pino пише для `err`), — центральне правило замість правок у кожному місці;
- `refreshToken` у `onMessage` при `RedisUnavailableError` не логує взагалі (інцидент уже зафіксовано модулем здоров'я) і перериває обробку повідомлення (розділ 4);
- `logger.error` у login/logout/logoutAll/revoke лишаються, але з `err` типу `RedisUnavailableError` транспорт їх у Sentry не пропустить.
- **Свідоме рішення щодо stdout:** записи рівня `error` із цих місць під час збою лишаються в stdout на кожен запит — це діагностика конкретних запитів, і їх обсяг обмежений самими запитами. Обмеження «раз на хвилину» діє лише для модуля здоров'я. Якщо обсяг логів стане проблемою, наступний крок — понизити ці записи до `warn` за типом помилки, а не прибирати.

### 4. Поведінка в кожному місці і бюджет часу

| Місце                                         | «Сесії немає»                  | «Redis недоступний»                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| --------------------------------------------- | ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| HTTP (`handleError`)                          | як зараз                       | `503 service_unavailable`, `Retry-After: 1`, без тексту ioredis навіть у `APP_ENV=local`                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| WS-повідомлення (`onMessage`)                 | `closeExpiredSession` як зараз | з'єднання **не закривається**; відповідь на це повідомлення — у тому ж форматі, що `createWsRateLimitErrorResponse`: `{ status: "error", event: <початковий event запиту>, error: { code: "service_unavailable", … }, data: null, timestamp }`, тож фронтенд (`messageHandler` шукає колбек за `data.event`) одразу відхиляє відповідний Promise, а не чекає клієнтського таймауту                                                                                                                                                 |
| `refreshToken` перед прикладним повідомленням | —                              | недоступність → без логу, обробка повідомлення одразу завершується відповіддю `service_unavailable` (без другої команди)                                                                                                                                                                                                                                                                                                                                                                                                           |
| Heartbeat `ping`                              | —                              | **`pong` надсилається завжди, першим і без жодної Redis-команди**: heartbeat підтверджує транспорт, а не Redis. Фронтенд шле `ping` кожні 10 с і закриває з'єднання, якщо `pong` не прийшов за 5 с ([`websocket-heartbeat.ts`](../../packages/frontend/src/utils/websocket-heartbeat.ts)). Зараз `pong` іде лише після `await` refresh — тобто при повільному Redis з'єднання закривається вже сьогодні. Refresh токена для `ping` (продовження TTL 120 с) виконується **після** `pong` і не блокує його; недоступність — без логу |
| WS upgrade                                    | як зараз (пункт 18 — окремо)   | `503` з `Retry-After: 1` до `res.upgrade`, без `4001`; після першої недоступної команди друга (`get` сесії) не виконується                                                                                                                                                                                                                                                                                                                                                                                                         |
| `wsSessionHandler` / `verifyUpgradeToken`     | `{ kind: "missing" }`          | `{ kind: "unavailable" }`; успіх — `{ kind: "ok", … }` замість `null`/значення                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

**Бюджет часу.** Коли з'єднання розірване, `withRedis` відмовляє одразу (без команди), тож запит завершується за мілісекунди. Таймаут діє лише для підключеного, але повільного Redis, і **перша ж** недоступна команда перериває запит — наступні не виконуються. Тому час **очікування Redis** у запиті ≤ `REDIS_COMMAND_TIMEOUT_MS` × (кількість команд на шляху запиту). Це оцінка саме Redis-очікування, а не загальна межа запиту:

| Шлях                      | Redis-команди (послідовно)                                    | Найгірше очікування при таймауті 500 мс |
| ------------------------- | ------------------------------------------------------------- | --------------------------------------- |
| WS-повідомлення           | refresh `expire`, `getex` сесії                               | ≈ 1 с                                   |
| WS upgrade                | `get` токена, `get` сесії                                     | ≈ 1 с                                   |
| HTTP, наявна сесія        | `getex`                                                       | ≈ 0,5 с                                 |
| HTTP, нова анонімна сесія | `getex` + `setex`                                             | ≈ 1 с                                   |
| HTTP, відновлення CSRF    | `getex`, `getex` усередині `updateSessionData`, `setex`       | ≈ 1,5 с                                 |
| login                     | читання сесії, `setex` нової, `del` старої, `setex` WS-токена | ≈ 2 с                                   |
| logout                    | читання, `del`, `setex` нової анонімної                       | ≈ 1,5 с                                 |
| `logoutAll`               | цикл `SCAN` + `DEL`                                           | ≤ дедлайн операції 2 с (див. нижче)     |

Загальної межі часу HTTP-запиту план **не** вводить; повільний, але підключений Redis може розтягнути login до ~2 с, а `logoutAll` — довше. **Контракт `logoutAll` (`destroyAllSessions`):**

- Дедлайн операції `REDIS_LOGOUT_ALL_DEADLINE_MS`, default `2000` мс, рахується від початку циклу `SCAN`/`DEL`.
- **Залишок бюджету враховується на кожному `await`:** перед кожною командою обчислюється `remaining = deadline − now`; якщо `remaining ≤ 0` — цикл зупиняється; інакше команда очікується не довше `min(remaining, REDIS_COMMAND_TIMEOUT_MS)` (власний таймер поверх `commandTimeout`). Коли спрацьовує таймер — цикл зупиняється з `503`, навіть якщо команда ще виконується на сервері (`DEL` ідемпотентний, наступний виклик дочистить). Так операція завершується не пізніше `deadline` + кілька мілісекунд, а не `deadline` + таймаут поточної команди.
- Успіх (`{ status: "success", deletedCount }`) повертається **лише** якщо `SCAN` пройшов до курсора `0`. Тоді всі сесії користувача видалено.
- Якщо дедлайн вичерпано або будь-яка команда циклу отримала `RedisUnavailableError` — `503 service_unavailable` з `Retry-After: 1`, **без** `deletedCount` і без повідомлення про успіх. Відповідь не дає підстав показати успіх: метод `api.logoutAll` на фронтенді повертає помилку. Екрана «вийти з усіх пристроїв» у фронтенді зараз немає (є лише метод API), тож повідомлення «не вдалося, повторіть» з'явиться разом з екраном — поза обсягом цього плану.
- Уже видалені сесії лишаються видаленими: `DEL` ідемпотентний, повтор `logoutAll` дочищає решту з початку `SCAN`.
- `logger.warn` з `userId` і кількістю видалених на момент зупинки (без токенів). Default `500` мс підтверджується вимірюванням.

Фронтенд: перевірити, що WS-помилка `service_unavailable` з початковим `event` відхиляє Promise (`useWebSocketConnection.ts`, `messageHandler`) і не викликає перепідключення, а HTTP-клієнт показує загальну помилку сервера на `503`.

### 5. Що поза обсягом

4. Шар сесій: `withRedis` у `redis-session-storage.ts`, `ws-session-auth.ts`, `generate-ws-token-service.ts`; дедлайн `REDIS_LOGOUT_ALL_DEADLINE_MS` для циклу `SCAN`/`DEL` у `destroyAllSessions` з контрактом «успіх лише при курсорі 0, інакше `503`».
5. `handleError`: `RedisUnavailableError` → `503`.
6. `wsSessionHandler`, `verifyUpgradeToken`: результат `ok | missing | unavailable`; `onMessage` (спершу `pong` без Redis, потім refresh) і `handleUpgrade` за таблицею розділу 4.
7. Фронтенд: перевірка обробки `503` (зокрема `api.logoutAll` повертає помилку, а не успіх; UI для `logoutAll` не існує і в обсяг не входить) і WS-помилки `service_unavailable`.
8. `.env.example`, документація (`configuration.md`, `request-lifecycle.md`, `observability.md`, `websocket.md`, таблиця відмови Redis в `auth-security.md`), пункт 70 у code-issues.

## Тести

**Unit (без мережі):**

- `isRedisUnavailable`: кожна помилка ioredis зі списку → `true`; `WRONGTYPE`, помилка Lua, `SyntaxError` → `false`.
- `withRedis`: `status !== "ready"` → `RedisUnavailableError` без виклику операції; помилка недоступності → загорнута; інша помилка → пробрасується.
- `redis-health`: серія помилок дає **одну** `logger.error` з `sentryCapture`; повтор у межах інциденту — лише обмежений `warn`; відновлення за кожним із трьох сигналів (успішна команда, фоновий `PING`, `ready`) → `recovered`; новий інцидент знову дає одну подію; таймер `PING` працює лише в стані `unavailable`.
- `sentryStream`: запис з `err.type === "RedisUnavailableError"` не викликає `captureException`; інші `error` — як зараз.
- `handleError(RedisUnavailableError)` → `503`, `Retry-After: 1`, тіло без тексту ioredis (і в `APP_ENV=local`).
- `onMessage`: refresh недоступний → відповідь `service_unavailable` з початковим `event`, сесія не читається, з'єднання не закривається, `logger.error` не викликається; `missing` → `closeExpiredSession`; `ping` при недоступному Redis → `pong` надіслано **до** будь-якої Redis-команди і без очікування refresh (refresh для `ping` викликається після `pong`, його помилка не логується); з'єднання не закривається.
- `handleUpgrade`: токен недоступний → `503`, друга команда не виконується; abort під час `await` → жодного запису в `res`.
- Фронтенд: `messageHandler` з `status: "error"`, `code: "service_unavailable"` і відомим `event` відхиляє відповідний Promise одразу.

**Інтеграційні (`test:redis`, реальний Redis):**

- Під `CLIENT PAUSE WRITE` операція сесії падає за ≈ `REDIS_COMMAND_TIMEOUT_MS` і класифікується як `RedisUnavailableError`.
  Спільна методика для тестів повторів:

- **Команда точно відкладена паузою до `CLIENT KILL`:** `qbuf > 0` для цього не годиться — Redis може вже розібрати команду в аргументи й очистити буфер, лишивши виконання відкладеним (`processInputBuffer`). Сигналом є стан конкретного клієнта в `CLIENT LIST ID <id>`: прапорець блокування (`b` у `flags`) і ім'я відкладеної команди (`cmd=setex` / `cmd=del`). **Spike (2026-10-21, локальний Redis 7.4.11):** під `CLIENT PAUSE 3000 WRITE` клієнт з відкладеним `SETEX` показується в `CLIENT LIST` як `flags=b … qbuf=0 … cmd=setex`, а `INFO clients` дає `blocked_clients:1`. Тобто `qbuf` справді вже `0`, а надійний сигнал — `flags` містить `b` і `cmd` збігається з очікуваною командою. Перший прогін у CI (`redis:7-alpine`) має підтвердити те саме; якщо ні — тест падає з явним повідомленням. Якщо прапорця на цій версії немає, резервний сигнал — зростання лічильника заблокованих клієнтів в `INFO clients` разом із `cmd` клієнта. Тест чекає сигналу з обмеженим часом і падає з явним повідомленням, якщо сигнал не з'явився, а не мовчки чекає таймауту.
- **Контрольний прогін з повною конфігурацією повторів:** `enableOfflineQueue: true`, `autoResendUnfulfilledCommands: true`, `maxRetriesPerRequest: null` (або ≥ 1) і `commandTimeout` більший за час reconnect — інакше ioredis очистить чергу вже при розриві або відхилить команду таймаутом, і повтору не буде навіть у контролі. Той самий сценарій у контролі мусить **падати** (ключ з'являється після reconnect). Тільки тоді основний прогін з налаштуваннями розділу 1 доводить відсутність повтору.

- **Повтору немає — запис:** початкового ключа немає; `CLIENT PAUSE WRITE`, `saveSession(S)`, очікування сигналу відкладеної команди, `CLIENT KILL`, `CLIENT UNPAUSE`, очікування reconnect → ключа **немає**. Контроль — ключ є.
- **Пізнє виконання задокументоване:** `CLIENT PAUSE WRITE`, `saveSession` отримує таймаут, `CLIENT UNPAUSE` без розриву → ключ **з'являється** (накопичена команда виконується після паузи). Тест фіксує визнану поведінку з розділу 1, а не заперечує її.
- **Повтору немає — logout:** сесія існує; та сама послідовність з `destroySession` → після reconnect сесія **лишається** (`DEL` не повторився); повторний `destroySession` її видаляє. Контроль — сесії немає.
- **Застарілий знімок (рівень запису):** ключ містить `V0`; `CLIENT PAUSE WRITE`, `saveSession(A)`, очікування сигналу відкладеної команди, `CLIENT KILL`, `CLIENT UNPAUSE`, reconnect → ключ містить `V0` (A не повторено); потім `saveSession(B)` → `B`. Тест іде на рівні `saveSession` (`SETEX`), бо `updateSessionData` спершу читає сесію через `GETEX`, який теж змінює TTL і теж блокується паузою записів — тоді розрив прийшовся б на читання, а не на запис.
- **`updateSessionData` (unit):** порядок «`getSession` → `saveSession` з об'єднаними даними»; якщо читання повертає `RedisUnavailableError` — запису немає.
- **`logoutAll`:** при вичерпаному дедлайні або недоступності посеред циклу — `503`, без `deletedCount`; повторний виклик дочищає решту і повертає успіх.
- **`logoutAll`, команда перед самим дедлайном (unit, фейковий час):** `SCAN` повертає курсор ≠ 0, час доходить до `deadline − 10 мс`, наступна команда «висить» → відповідь `503` приходить не пізніше `deadline` + ε, а не `deadline − 10 мс + REDIS_COMMAND_TIMEOUT_MS`.
- **Відновлення здоров'я без reconnect:** `CLIENT PAUSE WRITE` → команда отримує таймаут, стан `unavailable`, одна подія; `CLIENT UNPAUSE` без розриву → наступна успішна команда (або фоновий `PING`) повертає стан `healthy` з `recovered`; новий збій дає нову подію.
- Розірване з'єднання: команда відхиляється одразу (без очікування таймауту); клієнт перепідключається сам.

**Ручна перевірка (два процеси бекенду, окремий Redis, як у feat-013):**

- Зупинка Redis більш ніж на 20 с: WS-з'єднання **живуть** (heartbeat `ping`/`pong` триває, фронтенд не закриває з'єднання), прикладні запити через WS отримують `service_unavailable`; HTTP отримує `503` за мілісекунди; у Sentry-логах одна подія `Redis unavailable` на процес; активні WS-з'єднання **не** закриваються, запит через WS отримує `service_unavailable` з тим самим `event`; новий upgrade отримує `503`.
- Повернення Redis: `Redis recovered` у логах; без рестарту HTTP і WS працюють, сесії на місці.
- Вимірювання p99 операцій сесії локально і (за можливості) у цільовому оточенні → підтвердити або змінити default `REDIS_COMMAND_TIMEOUT_MS`.

## Ризики

- **Хибні `503` під навантаженням**, якщо p99 Redis наближається до таймауту. Пом'якшення: вимірювання і змінна оточення.
- **Короткий reconnect дає `503`**, а не коротку затримку (ціна відмови від черги). Пом'якшення: `Retry-After: 1`, WS не закривається.
- **Запізніле виконання вже надісланої команди** після таймауту (розділ 1) — обмежені наслідки, задокументовано.
- **Зміна контракту** `wsSessionHandler`/`verifyUpgradeToken` зачіпає всіх викликачів; покривається unit-тестами.

## Відкриті питання

- Default `REDIS_COMMAND_TIMEOUT_MS`: `500` мс чи інше значення після вимірювань.
- Чи оформити це окремою фічею в `feature_list.json` разом із пунктом 35 (readiness), який використає `redis-health.ts`.
