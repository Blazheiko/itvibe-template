## Принцип

Ліміти бувають двох видів, і в них різні задачі:

1. **Захист інстансу (in-memory, per-process).** Не дає одному клієнту часто запускати тяжкі операції на конкретному процесі: парсинг тіла, middleware, запити до БД, виклики AI. Перевірка має бути миттєвою і нічого не коштувати; точність у масштабі кластера не потрібна. З N інстансами ефективний бюджет N×, і це прийнятно: кожен процес захищає себе сам.
2. **Бізнес-ліміти чутливих операцій (Redis, спільні).** Реєстрація, вхід, зміна і скидання пароля, SMS, прив'язка email/телефону. Тут потрібен саме спільний бюджет: N× спроб перебору пароля чи відправок SMS — це вже вразливість або гроші. Ці ліміти живуть у сервісах (`consumeAuthThrottle`), а не в HTTP-шарі.

**WebSocket upgrade** поєднує обидва: спершу локальний фільтр (захист процесу, без I/O), потім спільний бюджет у Redis (флуд з'єднань по кластеру).

## Розподіл

| Ліміт                         | Де                                            | Сховище                   | Чому                                                   |
| ----------------------------- | --------------------------------------------- | ------------------------- | ------------------------------------------------------ |
| HTTP L1 (усі API-запити з IP) | `checkGlobalRateLimit`, `server.ts:479`       | memory                    | захист інстансу; синхронна перевірка до `res.onData()` |
| HTTP per-route / per-group    | `checkRateLimit`, `server.ts:480`             | memory                    | захист інстансу від частих тяжких операцій             |
| Auth-операції                 | `consumeAuthThrottle` у сервісах              | **Redis** (є, розширюємо) | спільний бюджет на чутливі дії                         |
| WS upgrade, рівень 1          | `checkUpgradeRateLimit`, `ws-handlers.ts:422` | memory (є)                | відсікає флуд до будь-якого I/O                        |
| WS upgrade, рівень 2          | новий виклик після рівня 1                    | **Redis** (нове)          | спільний бюджет з'єднань по кластеру                   |
| WS-повідомлення               | `checkRateLimitWs`, `ws-rate-limit.ts:67`     | memory                    | захист інстансу; з'єднання живе на одному процесі      |

### Чому HTTP лишається in-memory

- **Синхронність.** Перевірка стоїть до реєстрації `res.onData()` (`server.ts:470–480`). Якщо там буде `await`, uWS може доставити тіло малого POST раніше, ніж `readData` зареєструє обробник, і запит зависне. Обійти це можна лише переробкою читання тіла (eager-буфер + `pause()`), а це складність і ризик заради лімітів, яким точність у кластері не потрібна.
- **Ціна.** L1 рахує кожен API-запит; у Redis це +1 RTT і навантаження на кожен запит.
- **Задача.** Ці ліміти захищають процес, а не бізнес-правило. Для бізнес-правил є `consumeAuthThrottle`.
- **Ліміт на вході** за потреби дає nginx `limit_req`, але він спільний лише в межах одного екземпляра nginx ([deployment.md](../../documentation/backend/deployment.md)); кілька nginx потребують власного рішення на рівні балансувальника.

### Чому WS-повідомлення лишаються in-memory і за IP

З'єднання завжди обслуговує один процес, тож лічильник повідомлень природно локальний; Redis додав би RTT на кожне повідомлення без користі для захисту процесу. Ключ лишається `ws-msg:<ip>:<url>`: перехід на `uuid` з'єднання дозволив би множити бюджет, відкриваючи нові з'єднання.

## Поточний стан Redis-механізму auth (перевірено в коді)

[`auth-throttle-service.ts`](../../packages/backend/src/app/services/auth/auth-throttle-service.ts): `consumeAuthThrottle({ scope, key, limit, windowSeconds })`, Lua `INCR` + `EXPIRE`, ключ `auth:throttle:<scope>:<key>`.

| Потік                     | Scope                                                              | Ключ        |
| ------------------------- | ------------------------------------------------------------------ | ----------- |
| Реєстрація email          | `register_email_ip`, `register_email_identifier`                   | IP, email   |
| Реєстрація телефоном      | `register_phone_ip`, SMS send                                      | IP, телефон |
| Підтвердження телефону    | `confirm_phone_ip`                                                 | IP          |
| Скидання пароля телефоном | `reset_phone_ip`, SMS send, `confirm_reset_phone_ip`               | IP, телефон |
| Прив'язка телефону        | `link_phone_ip`, SMS send, `confirm_link_phone_ip`                 | IP, телефон |
| Прив'язка email           | `link_email_target`, `link_email_user`, `link_email_user_cooldown` | email, user |

Особливості:

- **Fixed window, яке не зсувається.** `EXPIRE` викликається лише при `count == 1`, тож вікно закінчується через `windowSeconds` від першої спроби. Відхилені спроби збільшують лічильник, але кінець вікна не пересувають.
- **Fail-closed:** помилка Redis загортається в `tryInternal` і дає внутрішню помилку, запит відхиляється. Для чутливих операцій це правильно.
- Спільний клієнт ioredis без `commandTimeout` і з offline queue: при недоступному Redis запит чекає, а не падає швидко.

**Прогалини (лише in-memory ліміти):**

- `POST /auth/login` — вхід за паролем; найважливіша прогалина. Відповіді вже здебільшого однакові: відсутній акаунт, неправильний пароль, вимкнений phone-auth і невалідний телефон дають `unauthorized("Invalid email or password")`. Відрізняється лише акаунт без пароля: `badRequest("Please use social login for this account")` — це розкриває, що акаунт існує і створений через OAuth.
- `POST /auth/change-password` — перевіряє поточний пароль (`auth-service.ts`, `validatePassword(currentPassword, …)`), тобто це теж перебір пароля, хоч і для автентифікованого користувача.
- `POST /auth/forgot-password`, `POST /auth/reset-password`, `POST /auth/verify-email`, `POST /auth/resend-verification-email`.
- Частина контролерів не передає IP у сервіс: наприклад, `AuthController.resetPassword` викликає `passwordResetService.resetPassword(token, password, passwordConfirm)` без `requestMeta`.

## Що робимо

### 1. Окремий Redis-клієнт для лімітів

Окреме з'єднання (`database/redis-rate-limit.ts`) для `consumeAuthThrottle` і upgrade-ліміту.

**Це друге з'єднання до того самого Redis-сервера, а не окремий інстанс Redis.** Клієнт бере ті самі `REDIS_HOST`, `REDIS_PORT`, `REDIS_PASSWORD` і `REDIS_PREFIX` з [`config/redis.ts`](../../packages/backend/src/config/redis.ts); нових змінних для адреси немає, інфраструктура не змінюється. Ціна — одне додаткове TCP-з'єднання на кожен процес бекенду.

**Чому окреме з'єднання, а не налаштування спільного клієнта.** У ioredis `commandTimeout`, offline queue і повторне надсилання команд задаються на весь клієнт, а не на окрему команду. Для лімітів потрібна жорстка поведінка (швидка помилка, без черги, без повтору — інакше перевірка висить або квота списується двічі), а для сесій і WS-токенів — терпима до коротких збоїв (краще почекати, ніж розлогінити користувача). Змінити налаштування спільного клієнта означало б зачепити сесії; обгортка `Promise.race` поверх спільного клієнта не скасовує команду в черзі ioredis і не вимикає повтор, тож гарантій не дає.

**Окремий інстанс Redis** потрібен лише тоді, коли навантаження від лімітів має бути ізольоване від сесій (напр. дуже великий потік upgrade-перевірок). У цій задачі такої потреби немає; якщо з'явиться, достатньо дати клієнту лімітів власні змінні адреси.

Контракт клієнта:

- `enableOfflineQueue: false` — до стану `ready` і під час reconnect команди одразу отримують помилку, а не стають у чергу.
- `maxRetriesPerRequest: 0` і явно `autoResendUnfulfilledCommands: false` — команда не надсилається повторно після розриву. Це дві окремі опції; друга в ioredis 6 за замовчуванням `true`, тож задається явно. Reconnect при цьому лишається увімкненим (`retryStrategy` з обмеженою затримкою), це окремий механізм.
- `commandTimeout` — обмежує лише очікування відповіді, **не скасовує** виконання Lua: після таймауту операція могла вже спожити квоту. Тому таймаут трактується як «результат невідомий» і обробляється як помилка за політикою споживача (fail-closed для auth, fallback для upgrade), без повторного виклику.
- Значення `commandTimeout` обирається за вимірюваннями затримки до Redis у цільовому оточенні (p99 + запас); 50 мс — лише стартова оцінка. Змінна `RATE_LIMIT_REDIS_TIMEOUT_MS`.
- Обробник `error` логує з обмеженням частоти (не частіше разу на хвилину), щоб розрив не засипав лог.
- Закриття клієнта в `stopGracefully` (`src/index.ts`) поряд з основним Redis.

### 2. WS upgrade: локальний фільтр → Redis → автентифікація

Порядок у `handleUpgrade`:

1. **Рівень 1, memory** — наявний `checkUpgradeRateLimit`, синхронно, до будь-якого I/O. Поріг вищий, ніж зараз, бо його задача — лише захист процесу від флуду (підтверджено: 120 / 60 с).
2. **Рівень 2, Redis** — `await checkUpgradeRateLimitShared(ip)`, спільний бюджет на кластер (підтверджено: 60 / 60 с). Після `await` перевірити `aborted`; якщо `true` — нічого не писати в `res`.
3. Перевірка токена й сесії (`onUpgrade`) — як зараз.

Redis-реалізація — новий `vendor/utils/rate-limit/redis-sliding-log.ts`, Lua sliding-log на ZSET із семантикою in-memory store:

- час — `redis.call('TIME')`, а не `Date.now()` інстансу;
- `ZREMRANGEBYSCORE` старших за вікно → `ZCARD` → якщо `< max`: `ZADD` + `PEXPIRE windowMs`; інакше `retryAfter` від score елемента з індексом `card − max`;
- **member обов'язково унікальний** (`<мікросекунди з TIME>-<nonce>`, де nonce — `crypto.randomUUID()` запиту, переданий у `ARGV`; додаткового Redis-ключа немає, тож нема чого накопичуватися й очищати): `ZADD` для наявного member лише оновлює score, тож однаковий timestamp у конкурентних запитах інакше «з'їв» би спробу;
- відхилені спроби не пишуться, `retryAfterMs` точний; ключ `rl:upgrade:<ip>` поверх `REDIS_PREFIX`.

Змінні: `WS_UPGRADE_RATE_LIMIT_*` (рівень 1, є) і нові `WS_UPGRADE_SHARED_RATE_LIMIT_WINDOW_MS`, `WS_UPGRADE_SHARED_RATE_LIMIT_MAX` (`MAX=0` вимикає рівень 2, напр. для одного інстансу).

### 3. Відмова Redis: два різні сценарії

| Сценарій                                                                          | Upgrade, рівень 2                                | Автентифікація upgrade                                                                                                           | Auth-throttle                                                                                                |
| --------------------------------------------------------------------------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Збій лише з'єднання лімітів (розрив, таймаут під навантаженням; сервер доступний) | пропускається; діє рівень 1 (локальний) + `warn` | працює через основний клієнт                                                                                                     | fail-closed: auth-запити відхиляються                                                                        |
| Недоступний Redis-сервер                                                          | пропускається; діє рівень 1                      | **не працює**: `verifyUpgradeToken` читає Redis через основний клієнт без короткого таймауту і чекає ~45 с (20 повторів ioredis) | запит не доходить до throttle: middleware сесії чекає ~45 с і завершується `500` (перевірено вручну, етап 9) |

Обидва з'єднання ведуть до одного сервера, тож на практиці найчастіший сценарій — другий (сервер недоступний). Перший виникає, коли саме з'єднання лімітів розірване або не вкладається у свій короткий `commandTimeout`, а основний клієнт (без короткого таймауту) ще отримує відповіді.

Fallback відновлює лише локальне обмеження і не гарантує успішного WS-з'єднання. Зараз `handleUpgrade` допускає `dataAccess === null` і робить `res.upgrade`, а з'єднання закривається вже в `onOpen` кодом `4001` (`ws-handlers.ts`). Це окремий пункт 18 у code-issues; тут не виправляється, але документація має описувати фактичну поведінку.

Після відновлення Redis лічильники рівня 2 починаються з того стану, що лишився в Redis; спроби, пропущені локально під час відмови, у спільний бюджет не потрапляють. Допустиме перевищення за вікно після відновлення — до `N × поріг рівня 1` (кожен інстанс рахував окремо). Це фіксується в документації як очікувана поведінка.

### 4. Login-політика

Рішення (підтверджено власником 2026-10-21):

- **Що рахується:** кожна допущена спроба входу, незалежно від результату. Спроба атомарно споживається наявним `consumeAuthThrottle` **до** пошуку користувача й перевірки пароля. Розділеної схеми «перевірити зараз, інкрементувати після невдачі» немає: вона має гонку — багато одночасних запитів бачили б вільний бюджет і всі доходили б до перевірки пароля. Валідаційні помилки тіла не рахуються (їх відсікає валідатор раніше).
- **Однаково для всіх результатів:** відсутній акаунт, неправильний пароль, акаунт без пароля — спроба вже спожита до пошуку, тож бюджет витрачається однаково.
- **Акаунт без пароля:** відповідь `Please use social login for this account` розкриває існування OAuth-акаунта. **Рішення: уніфікувати** до `unauthorized("Invalid email or password")`, як для відсутнього акаунта й неправильного пароля. UX: фронтенд показує в тексті загальної помилки підказку «або увійдіть через соцмережу». Тест: відповідь і HTTP-статус для акаунта без пароля збігаються з відповіддю для відсутнього акаунта.
- **Ключі:**
  - за IP — захист від перебору багатьох акаунтів з одного джерела;
  - за ідентифікатором — захист одного акаунта від розподіленого перебору. Ідентифікатор нормалізується точно як при пошуку: email через `normalizeEmail`, телефон через локальний `normalizePhone` з `auth-service.ts` (з тими самими налаштуваннями, що в `login`), а не напряму через `normalizePhoneNumber`. Нормалізацію винести в одну функцію `resolveLoginKey`, яку використовують і пошук, і throttle. Якщо ідентифікатор не нормалізується (невалідний телефон, вимкнений phone-auth) — рахується лише IP-лічильник.
- **Співвідношення порогів:** поріг за ідентифікатором **вищий** за поріг за IP, щоб один атакувальник не міг легко заблокувати чужий акаунт. Оскільки рахуються всі спроби, включно з успішними, пороги вищі, ніж були б для лише невдач. Підтверджені пороги: 20 спроб / 15 хв на IP, 40 спроб / 15 хв на ідентифікатор.
- **Тривалість блокування:** не постійне; до кінця fixed window (15 хв від першої спроби вікна). Прогресивних затримок у цій задачі немає.
- **Після успішного входу:** лічильник за ідентифікатором скидається (`DEL`), лічильник за IP — ні (інакше атакувальник з валідним власним акаунтом обнуляв би свій IP-бюджет). `DEL` після успіху не створює гонки на користь атакувальника: щоб його викликати, потрібен правильний пароль.
- Ризик lockout DoS лишається (атакувальник може вичерпати поріг ідентифікатора з багатьох IP); пом'якшення — вищий поріг і коротке вікно. Фіксується в документації.

Нові змінні: `AUTH_LOGIN_MAX_ATTEMPTS_PER_IP`, `AUTH_LOGIN_MAX_ATTEMPTS_PER_IDENTIFIER`, `AUTH_LOGIN_WINDOW_SECONDS`.

### 5. Решта auth-прогалин

- **`change-password`:** бюджет спроб за `userId` (підтверджено: 10 / 15 хв) у Redis, споживається атомарно до перевірки поточного пароля (та сама схема, що й у `login`, без гонки). Скидання після успішної зміни.
- **`forgot-password` (email):** throttle за IP і за нормалізованим email **до** пошуку адреси; поведінка й відповідь однакові для наявної й відсутньої адреси (пошук і відправка листа — лише після проходження throttle).
- **`resend-verification-email`:** за користувачем/email.
- **`reset-password`, `verify-email`** (перебір токенів): за IP.
- **Передача IP:** контролери, які зараз не передають IP (`resetPassword` та інші з цього списку), передають `{ ipAddress: context.httpData.ip ?? "" }` у сервіс, як інші auth-методи.

### 6. In-memory ліміти — без змін у коді

HTTP L1, per-route і WS-повідомлення лишаються на `rateLimitStore`. Змінюється лише документація.

### 7. Реєстр спільних лімітів: `config/throttle-policies.ts`

**Проблема.** Локальні ліміти описані декларативно: `rateLimit` у `defineRoute` і змінні в `config/rate-limit.ts`, тож з `http-routes.ts` видно, який маршрут має який ліміт. Спільні Redis-ліміти описані імперативно: понад десяток викликів `consumeAuthThrottle({ scope: "…", key, limit: authConfig.…, windowSeconds: 60 * 60 })` у `auth-service.ts` і `password-reset-service.ts`; `scope` і вікно записані прямо у викликах, повного переліку в одному місці немає. Нові ліміти з цього плану цю розкиданість лише збільшили б.

**Рішення.** Усі спільні ліміти описуються в одному реєстрі `packages/backend/src/config/throttle-policies.ts`:

```ts
export interface ThrottlePolicy {
  /** Частина Redis-ключа: auth:throttle:<scope>:<key> (для fixed-window). */
  scope: string;
  /** Що підставляється як key — для документації і рев'ю. */
  keyBy: "ip" | "email" | "phone" | "identifier" | "user";
  algorithm: "fixed-window" | "sliding-log";
  /** 0 вимикає політику — лише якщо disableable: true. */
  limit: number;
  /** Єдина одиниця вікна для всіх політик. */
  windowMs: number;
  /** Чи можна вимкнути політику через limit = 0 (напр. для одного інстансу). */
  disableable?: boolean;
  /** Поведінка, коли Redis не відповів. */
  /** reject — відхилити запит; skip — пропустити спільну перевірку і покластися на вже виконаний локальний рівень (без другого локального consume). */
  onRedisError: "reject" | "skip";
  /** Скидати лічильник після успішної операції (login, change-password). */
  resetOnSuccess?: boolean;
}

export const throttlePolicies = {
  loginIp: {
    scope: "login_ip",
    keyBy: "ip",
    algorithm: "fixed-window",
    limit: readInt("AUTH_LOGIN_MAX_ATTEMPTS_PER_IP", 20),
    windowMs: readInt("AUTH_LOGIN_WINDOW_SECONDS", 900) * 1000,
    onRedisError: "reject",
  },
  loginIdentifier: {
    scope: "login_identifier",
    keyBy: "identifier",
    algorithm: "fixed-window",
    limit: readInt("AUTH_LOGIN_MAX_ATTEMPTS_PER_IDENTIFIER", 40),
    windowMs: readInt("AUTH_LOGIN_WINDOW_SECONDS", 900) * 1000,
    onRedisError: "reject",
    resetOnSuccess: true,
  },
  registerEmailIp: {
    scope: "register_email_ip",
    keyBy: "ip",
    algorithm: "fixed-window",
    limit: authConfig.emailRegisterMaxAttemptsPerIpPerHour,
    windowMs: 3_600_000,
    onRedisError: "reject",
  },
  smsSendPhone: {
    scope: PHONE_SMS_SEND_THROTTLE_SCOPE,
    keyBy: "phone",
    algorithm: "fixed-window",
    limit: authConfig.smsMaxSendsPerPhonePerHour,
    windowMs: 3_600_000,
    onRedisError: "reject",
  },
  wsUpgradeShared: {
    scope: "upgrade",
    keyBy: "ip",
    algorithm: "sliding-log",
    limit: readInt("WS_UPGRADE_SHARED_RATE_LIMIT_MAX", 60, { min: 0 }),
    windowMs: readInt("WS_UPGRADE_SHARED_RATE_LIMIT_WINDOW_MS", 60_000),
    onRedisError: "skip",
    disableable: true,
  },
  // … решта наявних scope і нові з розділу 5
} as const satisfies Record<string, ThrottlePolicy>;

export type ThrottlePolicyName = keyof typeof throttlePolicies;
```

Правила:

- **Сервіси не передають `scope`, `limit` чи вікно:** лише політику й ключ — `consumeAuthThrottle(throttlePolicies.loginIp, ipAddress)`. Помилитися в рядку `scope` чи вікні у виклику неможливо.
- **Перенесення наявних викликів без зміни поведінки:** ті самі `scope` (а отже ті самі Redis-ключі `auth:throttle:<scope>:<key>`), ті самі значення й змінні `AUTH_*`. Наявні лічильники в Redis після деплою продовжують діяти.
- **Одна одиниця вікна — `windowMs`.** Значення в секундах (наявні `AUTH_*_SECONDS`, години у викликах) переводяться в мілісекунди в реєстрі; назви змінних оточення не змінюються. `consumeAuthThrottle` переходить з `EXPIRE <секунди>` на `PEXPIRE <windowMs>`: тривалість вікна і Redis-ключі ті самі, а ключі, створені старим кодом з `EXPIRE`, просто доживають свій TTL. Кожне значення має одне джерело: змінна оточення або константа в реєстрі, без дубля в коді виклику.
- **Вимкнення політики:** `limit = 0` дозволено лише політикам з `disableable: true` — зараз це лише `wsUpgradeShared` (`WS_UPGRADE_SHARED_RATE_LIMIT_MAX=0`, напр. для одного інстансу). Тоді виклик не звертається до Redis і одразу дозволяє; локальний рівень 1 продовжує працювати. Для auth-політик `0` — помилка конфігу на старті: вимкнути захист чутливої дії змінною оточення не можна.
- **Пороги лишаються в змінних оточення:** реєстр читає їх (через `authConfig` або власний `readInt`), а не дублює. Невалідні значення додаються до помилок конфігу й зупиняють старт через `validateRuntimeConfig()`, як у `config/rate-limit.ts`.
- **`onRedisError` задає поведінку явно для кожної політики:** auth — `reject` (fail-closed), upgrade рівня 2 — `skip`: рівень 2 пропускається, а рівень 1 уже спожив свою спробу, тож один upgrade витрачає рівно одну локальну спробу. Розділ 3 описує сценарії, а реєстр — що робить кожна політика.
- **`resetOnSuccess`** — лише для `loginIdentifier` і `changePasswordUser`; викликається окремою функцією `resetAuthThrottle(policy, key)`.
- **Тест реєстру:** усі `scope` унікальні; `windowMs > 0` для всіх; `limit > 0` для всіх, крім політик з `disableable: true`, де `limit >= 0`; `keyBy` і `algorithm` з дозволених значень; значення `0` в env для auth-політики дає помилку конфігу.
- **Тест вимкненого рівня 2:** при `wsUpgradeShared.limit = 0` Redis-клієнт не викликається (мок без жодного виклику), upgrade проходить через рівень 1 і далі; рівень 1 при цьому відмовляє, коли вичерпано його бюджет. Окремий тест перевіряє, що сервіси більше не викликають `consumeAuthThrottle` з літералом об'єкта (лише з `throttlePolicies.*`), напр. через пошук у вихідних кодах.
- **Локальні ліміти в реєстр не входять:** вони лишаються в `defineRoute` і `config/rate-limit.ts`, бо описують маршрут і процес, а не бізнес-правило.

## Тести

**Unit (без мережі, як вимагає `AGENTS.md`):**

- `handleUpgrade`, з моками бекендів:
  - рівень 1 відмовляє → Redis не викликається;
  - рівень 2: дозвіл / 429 / помилка → fallback;
  - abort під час `await` рівня 2 — для дозволу, для 429 і для fallback: після abort жодного виклику `res.*` (`writeStatus`, `end`, `upgrade`, `cork`).
- `login`: спроба споживається до пошуку користувача (мок викликається раніше за репозиторій); при вичерпаному бюджеті репозиторій і `validatePassword` не викликаються; однаковий інкремент для відсутнього акаунта, неправильного пароля й акаунта без пароля; скидання лічильника ідентифікатора після успіху, IP-лічильника — ні; `resolveLoginKey` дає той самий ключ, що й пошук (email у різному регістрі, телефон у різних форматах); невалідний ідентифікатор → лише IP-лічильник.
- `forgot-password`: throttle викликається до пошуку email; однакова відповідь для наявної й відсутньої адреси.
- `change-password`: бюджет за `userId`, скидання після успіху.
- Помилка або таймаут Redis у `consumeAuthThrottle` → запит відхиляється (fail-closed), повторного виклику немає.

**Інтеграційні з реальним Redis** — окремий набір `test:redis`, локально запускається при `REDIS_TEST_URL` (інакше `skip`):

- Lua sliding-log збігається з in-memory store на спільній таблиці кейсів;
- два клієнти ділять один бюджет upgrade;
- конкурентні виклики з однаковим `TIME` не втрачають спроб і не перевищують `max` (унікальність member);
- відхилені спроби не пишуться, `retryAfterMs` точний; `PTTL` ключа в діапазоні `(windowMs − δ, windowMs]`, де δ — час між командою і вимірюванням (напр. 1 с);
- `consumeAuthThrottle`: повторні відмови не поновлюють TTL — `PTTL` після кількох відмов не більший за `PTTL`, виміряний після першої спроби (кінець вікна фіксований);
- `consumeAuthThrottle` для login: N ≥ M конкурентних спроб при бюджеті M, без успішних входів і без скидання лічильника, допускають рівно M (атомарність); після завершення вікна бюджет відновлюється. Через `DEL` після успіху бюджет ідентифікатора обмежує лише спроби між скиданнями, а загальну кількість перевірок пароля за вікно стримує IP-бюджет (окремий кейс: успішний вхід скидає лише лічильник ідентифікатора);
- fallback → відновлення: після повернення Redis бюджет рахується з його стану; перевищення за вікно не більше за поріг рівня 1 на інстанс.

**CI:** набір `test:redis` **обов'язково** запускається в CI з сервісом `redis` (GitHub Actions `services:`), інакше постійний `skip` лишить Lua без перевірки. Зараз CI для тестів застосунку немає взагалі (є лише `docs.yml`, пункт 36 у code-issues), тож у цю задачу входить мінімальний workflow саме для `test:redis`; повний CI лишається пунктом 36.

**Ручна перевірка** — два процеси бекенду за одним Redis:

- upgrade-цикл по черзі на обидва порти → спільний бюджет, 429 від рівня 2;
- `login` з неправильним паролем по черзі на обидва порти → спільний ліміт; успішний вхід скидає лічильник ідентифікатора;
- збій лише з'єднання лімітів — відтворюється примусовим від'єднанням саме клієнта лімітів (`disconnect()` з вимкненим reconnect на час сценарію; для цього клієнт лімітів експортує тестовий хук або перевірка йде через інтеграційний тест, що керує клієнтом напряму). Короткий таймаут не підходить: локальний Redis може відповісти швидше; невідповідний порт не підходить, бо адреса спільна з основним клієнтом → upgrade обмежується локально, з'єднання встановлюється; auth-запити відхиляються;
- зупинка всього Redis → upgrade обмежується локально, але з'єднання не автентифікується; auth-запити відхиляються.

## Ризики

- Lockout DoS за ідентифікатором (розділ 4).
- +1 RTT до Redis на кожен upgrade, що пройшов рівень 1.
- Таймаут Redis-команди дає невідомий результат: квота могла бути спожита.

## Прийняті рішення

| Рішення                           | Значення                                                                           |
| --------------------------------- | ---------------------------------------------------------------------------------- |
| Login за IP                       | 20 спроб / 15 хв (`AUTH_LOGIN_MAX_ATTEMPTS_PER_IP`, `AUTH_LOGIN_WINDOW_SECONDS`)   |
| Login за ідентифікатором          | 40 спроб / 15 хв, скидання після успіху (`AUTH_LOGIN_MAX_ATTEMPTS_PER_IDENTIFIER`) |

| Акаунт без пароля                 | відповідь уніфікується до `Invalid email or password`                              |

Пороги, обрані під час реалізації (етап 5) за зразком наявних `AUTH_*`:

| Рішення                                     | Значення                                                                                   |
| ------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `forgot-password` за IP                     | 10 / год (`AUTH_FORGOT_PASSWORD_MAX_REQUESTS_PER_IP_PER_HOUR`)                             |
| `forgot-password` за email                  | 3 / год (`AUTH_FORGOT_PASSWORD_MAX_REQUESTS_PER_EMAIL_PER_HOUR`)                           |
| `resend-verification-email` за користувачем | 3 / год (`AUTH_RESEND_VERIFICATION_MAX_PER_USER_PER_HOUR`)                                 |
| `reset-password` за IP                      | 20 / год (`AUTH_RESET_PASSWORD_MAX_ATTEMPTS_PER_IP_PER_HOUR`)                              |
| `verify-email` за IP                        | 20 / год (`AUTH_VERIFY_EMAIL_MAX_ATTEMPTS_PER_IP_PER_HOUR`)                                |
| `change-password`                           | змінні `AUTH_CHANGE_PASSWORD_MAX_ATTEMPTS_PER_USER`, `AUTH_CHANGE_PASSWORD_WINDOW_SECONDS` |

`forgot-password` при вичерпаному бюджеті або помилці Redis відповідає тим самим загальним повідомленням (лист не надсилається), щоб відповідь не розкривала ні існування адреси, ні стан бюджету.

## Відкриті питання

- Значення `RATE_LIMIT_REDIS_TIMEOUT_MS` для production — після вимірювань у цільовому оточенні. Локально (етап 9): `EVAL` throttle-скрипта p50 0,37 мс, p99 1,6 мс, max 24 мс на 2000 викликів; default 50 мс лишається з запасом.
